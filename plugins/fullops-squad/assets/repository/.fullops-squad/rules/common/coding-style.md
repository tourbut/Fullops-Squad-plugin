# 공통 코딩 스타일

적용 범위와 프로젝트 우선순위는 [공통 규칙 안내](README.md)를 따른다.

## 단순한 설계

필요한 요구사항을 충족하는 가장 단순하고 명확한 구현을 선택한다. 미래의 사용을 추측해 기능·추상화·의존성을 추가하지 않는다. 실제 중복과 변경 이유가 확인됐을 때 공통화를 검토한다. 비슷하게 생겼다는 이유만으로 서로 다른 책임을 합치지 않는다.

기존 코드와 프로젝트 정본을 먼저 확인하고 일관된 이름·구조·관례를 따른다. 프레임워크가 이미 제공하는 계층을 불필요하게 감싸지 않는다. 아키텍처 변경은 근거와 영향을 기록하고 필요한 프로젝트 결정 절차를 따른다.

## 책임과 상태 변경

함수·모듈은 명확한 책임과 의존성 경계를 갖게 한다. 파일 길이와 중첩은 분리 필요성을 검토하는 신호이지 일률적인 실패 기준이 아니다. 생성물·외부 코드·테스트의 특성도 구분한다.

숨은 부작용과 불필요한 공유 상태를 줄인다. 상태 변경이 필요하면 소유권과 변경 경계를 명확히 한다. 불변성과 복사의 선택은 언어·프레임워크·성능 특성 및 프로젝트 관례를 따른다. 모든 객체 변경을 금지하지 않는다.

## 이름과 가독성

역할과 동작을 설명하는 이름을 사용하고 표기법은 프로젝트 관례를 따른다. 의미가 있는 한계값·지연·정책 값은 이름 있는 상수나 설정으로 표현한다. 분기 중첩이 이해를 방해하면 조기 반환이나 책임 분리를 검토한다. 주석은 코드의 반복 설명보다 이유·제약·주의점을 전달한다.

## 오류와 경계

외부 입력과 시스템 경계에서 스키마·타입·범위·권한을 검증한다. 오류는 복구·변환·전파 중 책임 있는 방식으로 처리한다. 오류를 숨기거나 실패를 성공으로 보고하지 않는다. 의도적인 대체 동작은 조건과 한계를 명시하고 테스트한다.

사용자에게는 안전하고 이해 가능한 오류를 전달하고, 내부에는 진단에 필요한 근거를 남긴다. 같은 예외를 모든 계층에서 중복 기록하지 않으며 비밀값과 민감정보를 로그에 넣지 않는다.
