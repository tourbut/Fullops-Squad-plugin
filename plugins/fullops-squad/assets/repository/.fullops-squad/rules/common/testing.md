## 테스트 레벨

`fullops.json.test_level`이 개발 검증 범위의 정본이다. 신규 setup은 lite, 기존 설정 누락은 standard다.
- `lite`: 변경한 핵심 동작과 필요한 실패 경계만 짧게 검증한다. 사소한 문구 변경에는 새 테스트를 만들지 않는다.
- `standard`: 변경 동작·실패 경계와 영향을 받는 연동의 회귀를 검증한다.
- `full`: 안정된 통합 후보에서 전체 회귀와 필요한 통합·수락 검사를 담당자별로 한 번 수행한다.

보안·데이터 손실 방지·프로젝트 필수 검사·독립 리뷰·최종 수락 조건은 모든 레벨에서 유지한다. 완료 조건에 선택 레벨·검사 담당·대상·시점을 기록하고 통과 뒤에는 새 변경·실패·근거 결함이 있을 때만 재검증한다.
lint.json의 test 명령에 최소 level을 명시하면 범위 밖 명령은 skipped와 사유를 남긴다. 레벨 없는 기존 명령과 required: true 명령은 항상 실행한다. 기준 merge-base의 설정을 사용하며 검사 생략을 PASS로 보고하지 않는다.

# 공통 테스트 기준

적용 범위와 프로젝트 우선순위는 [공통 규칙 안내](README.md)를 따른다.

## 기준과 범위

`project.md`에서 실제 테스트·린트·타입 검사·빌드 명령과 실행 위치를 확인한다. 패키지 매니저와 테스트 실행기를 구분하고 존재하지 않는 명령을 추정해서 사용하지 않는다.

변경한 동작, 실패·경계 조건, 영향을 받는 연동을 검증한다. 단위·통합·E2E 테스트의 필요 여부와 커버리지 목표는 프로젝트 기준과 변경 위험에 따라 정한다. 일률적인 커버리지 80%나 모든 테스트 종류를 요구하지 않으며 기존 기준은 낮추지 않는다.

문서·설정·생성물 변경은 링크·스키마·빌드 등 적합한 검증을 선택한다. 적용하지 않는 검증과 그 이유를 기록하고 실행하지 않은 검증을 통과로 보고하지 않는다.

## 담당과 반복 범위

지시서는 구현 담당자의 완료 조건과 제품 최종 수락 조건을 구분하고, 검사별 담당·대상·실행 시점·통과 조건을 정한다. 구현 담당자는 변경 동작의 자동 검사·관련 회귀·필요한 짧은 실행 확인을 맡는다. 독립 QA와 ART 직접 검수는 후속 담당에게 인계한다. 전담 역할이 없으면 담당과 독립 검토 방법을 지시서에 정한다.

전체 플레이·장시간 성능·반복 수명 검사는 기능과 에셋이 안정된 고정 통합 후보에서 지정 담당자가 실행한다. 구현 중에는 결함 재현과 개선 판정에 필요한 짧은 검사를 쓴다. 최종 수락용 전체 검사를 매 수정마다 반복하지 않는다.

캡처는 시각 판정이 필요한 지정 항목에만 만든다. 영상은 모션·깜빡임·시간에 따른 변화처럼 정지 화면으로 판정할 수 없는 항목에만 만든다. 통합 후보마다 필요한 자료를 한 번 확보해 검수자와 공유하며, 자동 검사로 판정되는 값·상태는 실행 결과로 남긴다.

재검증은 변경 영향, 새 실패, 기존 증거의 결함이나 미충족 조건이 있을 때 수행한다. 변경 없는 항목은 대상 코드·에셋·설정·환경 등 관련 의존성의 동일성을 확인하고 기존 실행 SHA·조건·증거를 연결해 재사용한다. 재사용 자료를 새 SHA의 실행이나 독립 QA로 바꾸어 기록하지 않는다. 공통 경계 변경으로 영향이 넓으면 그 범위의 회귀를 실행한다.

정한 검사가 끝나면 결과를 인계한다. 같은 실패는 원인·구현·검사 조건이 바뀌거나 새 근거가 있을 때 재시도하며, 반복으로 해결되지 않으면 실패·원인·남은 일·담당·재개 조건을 보고한다. 외부 자료·응답·장치 대기 중에는 새 검증을 추가하지 않는다. 기존 실패와 독립 QA·ART 검수·최종 수락 기준은 유지하며 미충족 조건을 PASS로 바꾸지 않는다.

## 재현과 실행

버그 수정은 가능한 경우 먼저 실패를 재현하는 테스트를 추가한다. 신규 동작도 실행 가능한 테스트를 먼저 정의하고, 프로젝트에서 요구하는 TDD 절차를 따른다. RED를 주장하려면 테스트가 실제 실행됐거나 의도한 컴파일 실패를 검증했는지 확인한다. 환경 오류나 관계없는 실패를 해당 결함의 재현으로 취급하지 않는다.

수정 후 같은 대상을 다시 실행하고 관련 회귀를 확인한다. 실패를 없애기 위해 근거 없이 테스트를 제거·완화하지 않는다. 테스트 자체가 잘못됐다면 기대 동작의 근거와 수정 이유를 남긴다.

## 테스트 작성

준비·실행·검증을 구분하고 테스트 이름에 관찰 가능한 동작을 표현한다. 순서·시간·외부 상태에 대한 의존을 줄이며, 대체 객체가 실제 계약을 왜곡하지 않는지 확인한다. 실제 외부 자원이 필요한 검증은 권한·비용·환경 조건을 명시한다.

## 검증 근거

지시서의 완료 기준과 검증 대상을 연결하고 명령·실행 위치·대상 코드 커밋 또는 변경 상태·결과·관련 로그를 QA 보고서나 상세 작업 로그에 기록한다. 실패·미실행·불안정한 테스트와 한계를 구분한다.

작업 기록 완료, 리뷰 기록 검사 통과, 테스트 성공, 병합 수락은 서로 다른 상태다. `work.py finish`나 `review.py check`만으로 테스트 성공을 주장하지 않는다.
