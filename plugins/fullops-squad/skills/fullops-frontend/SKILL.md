# 프런트엔드 디자인

## 1. 범위와 선택

`fullops.json`, `project.md`, 공통 코딩 규칙과 현재 역할 인박스를 읽는다. 활성 레포가 아니면 `setup-fullops`를 안내한다. UI 변경이 없는 작업에는 이 절차를 적용하지 않는다.

프로젝트 기본 선택은 `.fullops-squad/docs/agents/frontend.json`, 이번 과제의 선택은 역할 인박스가 정본이다. CLI 옵션은 이번 실행만 바꾸며 설정 파일을 덮어쓰지 않는다. 대화의 사용자 지정 → 이번 과제의 고정 tuple → 기존 프로젝트 설정 순으로 호스트·모델·effort를 보존한다. 호스트를 바꾸면 이전 제공사의 모델을 그대로 넘기지 않는다. 지정이 없으면 현재 세션 또는 기존 배정표의 확인된 tuple을 제안하고 미정 값만 확인한다. 브랜드별 우열을 전제로 자동 배정하지 않는다.

주 스킬은 한 개만 고른다. 사용자가 지정한 스킬을 우선하며 요청으로 선택이 분명하면 아래 기준으로 기록하고 진행한다.

| 작업 | 주 스킬 | 필요한 경우의 보조 검토 |
|---|---|---|
| 새 화면·시각 방향·화면 구현 | `frontend-design` | 코드 접근성 검토에 `web-design-guidelines` |
| 팔레트·폰트·스타일·디자인 시스템 검색 | `ui-ux-pro-max` | 기존 화면과의 일관성 검토 |
| 기존 화면 비평·audit·polish | `impeccable` | 코드 검토에 `web-design-guidelines` |

공통 네 스킬은 세 호스트에 설치되지만 주 스킬과 이번 보조 검토의 원문·참조만 읽는다. 실제 실행 전에 [도구 준비](toolchain.md)를 읽고 설치 상태와 런타임 검증 상태를 구분한다. 사용자가 이미 허용한 범위는 다시 묻지 않는다.

`python3 <플러그인>/scripts/frontend.py --repo <루트> --host <codex|claude-code|grok> --model <기존/지정 모델> --effort <기존/지정 effort> --check`로 선택한 구성의 준비 상태를 확인한다. 누락·미지원·인증 실패는 원인과 가능한 기존 경로를 제시하고 다른 호스트로 자동 전환하지 않는다. 이 check는 로그인·브라우저 QA·MCP 연결 성공을 뜻하지 않는다.

완료 조건: 대상 화면·범위, 호스트·모델·effort, 주 스킬과 보조 도구, 설치/실행/인증 상태를 인박스에 기록했다.

## 2. 디자인과 인계

기존 `DESIGN.md` 또는 project.md가 가리킨 정본을 config의 `design`에 연결한다. 기존 토큰·공용 컴포넌트 경로는 `tokens`·`components`에 연결하며 본문을 복제하지 않는다. 정본이 없으면 기존 화면·CSS·컴포넌트와 사용자 요구에서 방향을 정한 뒤 한 경로만 정본으로 지정한다. 새 정본 생성은 기존 디자인을 교체한다는 뜻이 아니다.

[지시서와 QA 계약](delivery.md)의 입력을 현재 `fullops-work` 인박스에 채운다. 선택한 외부 스킬의 원문과 해당 참조를 읽고 프로젝트 요구·정본에 맞춰 수행한다. 외부 스킬이 새 역할·subagent·hook·유료 서비스·외부 업로드를 요구하면 기존 FullOps 권한과 하위 위임 정책 범위에서만 실행한다.

coordinator가 배정하는 경우 `jev_route.py --model-only --role <역할> --key <키> --repo <루트> --agent <codex|claude|grok> --model <고정 모델> --effort <고정 effort>`로 tuple을 기록한다. 기존 역할 분류·패킷·dispatch·독립 리뷰 게이트는 그대로 따른다. 호스트 전환 시 인박스·정본·토큰·코드 SHA·기존 QA 증거를 같은 버전으로 전달한다. 같은 과제의 하위 작업도 고정 tuple과 위임 제약을 전달받는다.

완료 조건: 구현 전 유지/변경할 디자인, 기능 상태와 수락 기준이 기록됐고 담당자가 같은 정본·SHA를 읽을 수 있다.

## 3. 구현·비평·검증

공통 코딩 규칙의 디자인 정본·토큰·컴포넌트 우선 규칙을 적용한다. 비평 결과를 수락 기준과 대조하고 범위 안의 결함만 수정한다. 사용자 방향·사실 문구·제품 규칙 변경은 기존 질문 경로로 처리한다. 독립 비평이 필요하면 등록 역할·별도 세션으로 수행하며 세 모델을 매번 모두 호출하지 않는다.

`fullops-test`로 프로젝트 E2E → 필요한 조작 테스트 → 필요한 시각 판정을 수행한다. Jev 키가 없으면 기존 프로젝트 테스트나 선택한 로컬 브라우저 도구로 같은 수락 기준을 확인하고 사용한 대안을 기록한다. 검사를 할 수 없으면 `not_run`과 사유를 남긴다. 디자인 비평·CLI 존재 확인만으로 동작 QA나 접근성 적합성을 통과시키지 않는다. tester는 제품 코드를 수정하지 않는다.

완료 조건: 지시서가 지정한 검사와 디자인 lint 결과, 테스트 레벨이 요구하는 조작·캡처 증거, 미실행·잔여 결함이 기존 QA 경로에 있다. minimal·lite 개발 과제는 lint·변경 동작 테스트로 확인한다. 디자인 정본과 비교하는 작업용 캡처는 2~3회 고치는 데만 쓰고 커밋하지 않는다. 화면 품질은 큰 틀 검수(`rules/common/testing.md`)에서 본다.

## 4. 완료

`delivery.md`의 결과 항목을 기존 완료 보고와 `qa-reports/<과제 키>-test/`에 연결한다. `fullops-work`의 아카이브·`fullops-review`의 고정 SHA 독립 리뷰·critical/high 차단·통합 절차를 따른다. 미확인 호스트를 검증 완료로 올리지 않는다.

완료 조건: 구현 SHA, 선택 호스트/모델/도구 ref, 검증 근거, 미실행 사유와 후속 담당을 기록했다.
