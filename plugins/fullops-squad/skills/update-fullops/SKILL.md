# 릴리스 업데이트와 레포 적용

사용자는 `FullOps update 수행해줘`라고 요청하면 된다. 요청은 현재 CLI의 플러그인 업데이트와 현재 활성 레포에 필요한 후속 적용을 포함한다. 다른 제품·라이브러리 업데이트는 이 스킬의 대상이 아니다.

1. 현재 CLI, 실제 설치된 FullOps 패키지 경로·버전과 대상 레포를 확인한다. `.fullops-squad/fullops.json`의 `plugin_version`은 레포 적용 버전이며 설치 버전과 별도로 기록한다. 업데이트 전 실제 설치 버전을 먼저 확보하고 업데이트 기록에 남긴다. 버전을 추정하지 않는다. 진행 중 worker와 사용자 변경은 보존한다.
2. 패키지의 `../../INSTALL.md`에 있는 현재 CLI 업데이트 절차를 실행한다. 개발 체크아웃에서는 루트 README.md를 읽는다. 업데이트 요청은 이 설치 작업을 허가한다. 의존성은 새 패키지의 `../../scripts/deps.py --check`로 확인하고 누락분은 같은 도구의 `--host <현재 CLI>`로 설치한다. 실패한 명령은 기록하고 설치 성공으로 보고하지 않는다.
3. 실제 새 설치 경로와 버전을 다시 확인한다. 이전 캐시의 스킬·스크립트를 계속 쓰지 않고 새 패키지의 이 스킬을 직접 읽는다. 이전 세션의 hook은 남을 수 있으므로 이 세션에서는 운영 업데이트만 수행하고 제품 worker를 시작하지 않는다. 새 설치를 이 세션에서 확인할 수 없으면 확보한 이전 버전·남은 단계를 기록해 새 세션에서 이어간다.
4. 새 패키지의 `scripts/update.py --repo <루트> --from <업데이트 전 실제 설치 버전>`을 실행한다. 출력에는 레포 적용 버전과 두 버전 중 더 오래된 기준 이후의 모든 릴리스 본문·수행 절차가 포함된다. 설치만 먼저 갱신된 레포도 놓친 적용을 회수한다. `--json`은 같은 내용을 구조화해 출력한다. 이 스크립트는 레포를 수정하지 않는다. 신규 레포는 설치 확인 뒤 `setup-fullops`로 구성한다.
5. 릴리스를 오래된 순서로 읽고 `기존 레포 적용` 항목을 이 레포에 적용·해당 없음·보류로 분류한다. 출력만 전달하고 끝내지 말고 적용 가능한 항목을 수행한다. 선택 기능은 기존 합의와 역할 구성을 따르며 미정 제품 결정만 질문한다. 새 setup은 기존 역할로 dry-run한 뒤 실행하고 기존 문서는 필요한 절만 통합한다. 릴리스에 이 절이 없으면 변경 내용과 새 템플릿을 비교해 적용 여부를 기록한다.
6. `.fullops-squad/docs/exec-plans/phases/FULLOPS-UPDATE-<대상 버전>.md`에 업데이트 전 설치 버전·레포 적용 버전·대상 버전과 릴리스별 판정·근거·변경 파일·검증·보류 담당·재개 조건을 기록한다. 기존 기록은 보존하며 이어서 갱신한다. 문서 형식은 레포의 작성 규칙을 따른다. 완료한 동일 버전 재요청은 보류된 항목만 확인한다.
7. 필수 레포 적용과 관련 검증이 완료됐을 때만 `fullops.json`의 `plugin_version`을 실제 설치 버전으로 갱신한다. 역할·원격·기존 실패·검증 기록·제품 정지는 보존한다. 보류된 필수 적용이 있으면 이전 버전을 유지하고 다음 요청에서 이어간다. 작업 중 워크트리의 동기화 예약은 레포 적용과 구분해 기록한다.
8. 준비 변경을 커밋하고 허가된 범위에서만 push·워크트리 동기화를 수행한다. 진행 중 체크아웃은 덮어쓰지 않는다. 설치 버전·레포 적용 버전·반영 내용·검증·보류 사항과 기록 경로를 보고한다. 이후 개발은 새 coordinator 세션에서 진행한다.
