# FLOW-GRAPH-001 — 과제 생명주기를 명시한 흐름 그래프로 빈 게이트를 메우고 진행을 한눈에 본다

이 문서는 여러 과제에 걸치는 묶음 작업의 의도다. 과제는 명세 문서, hook·스크립트 알림, 상태 기록, fullops-meter mod다. 사용자가 승인하면 `status`를 `approved`로 바꾸고 `## 승인`에 근거를 적는다. 관련 이슈: #86(흐름 그래프 명세), #82(플레이북 로드맵), #59(사이드패널 다이어그램).

## 배경

FullOps는 이미 과제를 단계 순서대로 보낸다. 단계는 route → 지시서 → worker → `worker_done` → 리뷰 → 통합·병합 → 현황판이다. 단계 사이에는 결정론적 게이트가 있다. 예: flow_gate·done_gate 차단, lint 통과 기록, `review.py check`, `update.py --verify`, 증거 커밋 hook(#83·#84). 그러나 이 흐름을 한곳에 적은 문서가 없다. 어느 전환에 게이트가 있고 어느 전환에 없는지 알려면 코드를 읽어야 한다.

2026-10-22 점검(KnowsLink 기록, 읽기 전용)에서 게이트가 없는 전환에서 문제가 생겼다.

- 리뷰한 SHA와 병합한 SHA가 다른 병합이 있었다(LANG: 7704e6d 리뷰, b11d5b4 병합). 병합 193건 중 149건에 리뷰 필요성 판정 기록이 없다.
- SHA가 없는 통합 기록이 5건이다. 완료 보고 209건 중 125건에 300자가 넘는 줄이 있다.
- 과제 하나에 보고서 폴더가 9개 생겼다(FIX·RECHECK·LOWS). route 키 191개 중 39개가 차수형 키다. 수정 고리에 끝이 없다.
- 현황판과 fullops-meter는 과제 상태를 각자 문서에서 다시 읽거나 도구 호출로 추정한다.

외부 근거는 두 가지다. 첫째, 그래프 엔지니어링 실무 원칙이다. 노드마다 책임 하나, 타입 있는 엣지, 경계 검증, 반복 구간의 예산과 에스컬레이션, 대화와 분리된 제어 상태가 그 원칙이다. 둘째, Karpathy autoresearch 루프의 원칙이다. 숫자 검증자, 지표로 남기거나 버리기, 고정 예산이 그 원칙이다. "그래프 엔지니어링"을 Karpathy나 Anthropic이 발표했다는 주장은 확인되지 않았으므로 근거로 쓰지 않는다. 같은 자료는 "처리량이 병목일 때만 그래프 구조를 더한다"고 경고한다. FullOps의 문제는 처리량이 아니라 검증 공백과 끝없는 반복 고리다.

## 문제

- 유지보수자와 coordinator는 과제의 어느 전환이 자동으로 검증되는지 알 수 없다. 그래서 규칙 문장만 있는 전환에서 위반이 반복된다.
- coordinator는 병합할 때 리뷰한 SHA와 병합할 SHA가 같은지 확인할 장치가 없다.
- worker는 `worker_done`과 완료 보고를 자유 문장으로 보낸다. 브랜치·SHA·lint 결과가 빠져도 경계에서 걸러지지 않는다.
- 같은 과제의 수정·재검증이 몇 번째인지 아무도 세지 않는다. 그래서 고리가 사람에게 올라가지 않는다.
- 사용자는 여러 과제가 어느 단계에 있고 어디서 막혔는지 한 화면에서 보지 못한다.

## 바라는 결과

과제 생명주기가 노드·엣지·게이트를 가진 문서 하나로 명시된다. 비어 있던 경계 검증은 먼저 알림으로 채운다. 같은 과제의 반복은 정해진 횟수에서 사람에게 올라간다. coordinator가 총괄하는 과제 상태가 파일로 남는다. 사용자는 사이드패널에서 진행 중인 과제마다 현재 단계와 막힌 지점을 본다. LLM 호출은 늘지 않는다.

## 성공 기준

큰 틀 검수는 이 기준으로 판정한다. KnowsLink 수치는 적용 전후 같은 기간 길이의 git 기록으로 잰다. `확인할 흐름`은 과제 지시서가 정해진 뒤 채운다.

## 대상 사용자와 주요 흐름

- 플러그인 사용자: 사이드패널 Flow 탭에서 과제 목록을 본다 → 막힌 과제를 고른다 → 현재 노드와 막힌 이유(리뷰 차단, 반복 초과, intent 승인 대기)를 확인한다 → coordinator에게 결정을 준다.
- coordinator 에이전트: route → 지시서 → dispatch → `worker_done` 수신 → 리뷰 → 병합의 각 전환에서 상태 파일을 갱신한다 → 경계 알림이나 에스컬레이션 권고를 받으면 처리하거나 사용자에게 올린다.
- worker 에이전트: `worker_done`과 완료 보고를 정해진 필드로 보낸다 → 형식이 빠지면 알림을 받고 고친다.
- 플러그인 유지보수자: hook·스크립트를 바꿀 때 명세 문서를 함께 고친다. 명세와 코드가 어긋나면 테스트가 실패한다.

## 제약과 범위 밖

- 새 오케스트레이션 런타임이나 그래프 실행 엔진을 넣지 않는다. Orca와 기존 hook이 실행을 맡는다.
- LLM 호출을 늘리지 않는다. 모든 판정은 결정론적 코드다.
- 새 차단을 넣지 않는다. 이 묶음의 새 검사는 모두 알림이다. 오탐률을 본 뒤 차단으로 올릴지는 별도로 정한다.
- 기존 개념(역할 분리, 인박스, 독립 리뷰, 산출물 추적, 테스트 레벨)을 바꾸지 않는다.
- 과제별 위험도로 테스트 레벨을 자동으로 고르는 라우터는 만들지 않는다. 테스트 레벨은 사용자가 정한 값이고, 리뷰 강도는 `review.py need`가 정한다.
- 명세 문서는 플러그인 개발 문서다. 배포 패키지에 넣지 않는다.
- worker 세션은 바깥 상태 파일을 쓰지 않는다.
