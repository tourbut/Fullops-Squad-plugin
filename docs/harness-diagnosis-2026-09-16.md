# FullOps Squad 하네스 정밀 진단

진단일: 2026-09-16. 대상: 현재 dev 작업본. 아래 개선안은 제안이며 아직 구현하지 않았다.

## 1. 결론

현재 하네스는 **레포별 활성화, worker 인수인계, 기록 보존을 위한 초기 기반**이다. 그러나 **고성능 모델이 설계하고 더 저렴한 모델이 구현해도 품질이 유지되는 분업 체계**는 아직 구현되지 않았다. CLI 배정은 있지만 모델별 책임·명세 준비 조건·재작업 경로·독립 검수·비용 측정이 빠져 있다.

핵심 개선은 스킬 문장을 더 줄이는 것이 아니라, 구현 모델이 다시 설계하거나 전체 레포를 탐색할 필요가 없도록 입력을 확정하고 완료를 검증하는 것이다. 문서도 경로 목록만 제공하는 상태에서 실제 본문 템플릿과 공통 문체를 제공하는 상태로 바뀌어야 한다.

저렴한 모델을 쓰는 것은 호출 단가를 낮추는 방법이다. 총 토큰 수가 자동으로 감소하지는 않는다. 반복 구현·재설계·리뷰 왕복이 늘면 전체 비용과 시간이 오를 수 있다. 현재는 실제 모델 실행·사용량 계측이 없으므로 절감률이나 품질 유지율을 주장할 근거가 없다.

## 2. 확인 범위와 근거

- 스킬 4개, 플러그인 스크립트 3개, 통합 설치기, 의존성·호스트 매니페스트, setup 자산, 기존 테스트를 확인했다.
- 그래프 인덱스와 함수 검색·소스 조회를 사용하고, 문서·설정은 직접 읽었다.
- `python3 tests/check.py`: 통과. 기존 검증은 setup 보존과 기본 아카이브·경로 확인 중심이다.
- `python3 docs/diagnostics/harness-probes.py`: 임시 Git 레포에서 아래 7개 관찰을 재현했다. 실제 서비스 레포와 전역 설치는 변경하지 않는다.
- 자산 파일 36개 중 15개는 `.gitkeep`, 6개는 빈 역할 인박스다. setup은 이 파일들과 진입점·활성화 표식을 합쳐 40개를 만든다. 파일 수 자체를 토큰 비용으로 간주하면 안 된다. 비용은 무엇을 실제로 읽고 생성하는지에 달려 있다.
- 실제 Orca worker의 설계→구현→검수 전 과정, 모델별 품질·비용 비교, 전체 외부 의존성 설치는 이번 진단에서 실행하지 않았다.

## 3. 유지할 부분

1. 설치와 서비스 레포 setup 분리: 전역 설치와 프로젝트 활성화의 경계가 명확하다.
2. `.fullops-squad/` 격리: 기존 `.agents/`와 사용자 문서를 보존한다.
3. 지시서의 완료 기준·파일 소유권·복귀 주소: 분업에 필요한 입력의 출발점이다.
4. 워크트리 간 파일 가시성과 실제 착수 확인: 전송 성공을 착수로 오인하지 않도록 한다.
5. 원천 문서와 납품 인덱스 분리: 같은 내용을 두 번 작성하지 않는 방향이 맞다.
6. 파일 조작의 스크립트화: setup과 아카이브를 반복 생성하는 모델 출력을 줄인다.

## 4. 우선순위별 발견 사항

### P0 — 미완료 작업을 완료 처리할 수 있다

근거: [work.py:42–68](../plugins/fullops-squad/scripts/work.py), [fullops-work:23](../plugins/fullops-squad/skills/fullops-work/SKILL.md).

`finish`는 과제 키와 완료 보고가 템플릿 그대로인지 확인할 뿐, `blocked` 상태·미완료 체크박스·검증 결과·검토 수락을 확인하지 않는다. 보고란에 “테스트 실패, 구현 진행 중”을 추가해도 로그를 만든 뒤 인박스 전체를 비웠다. 원문은 로그에 남지만 진행 중 작업이 인박스에서 사라진다.

이전 규약의 “완료분만 제거하고 남은 작업 유지”와 현재 스크립트의 전체 삭제 사이에도 차이가 있다. 작업 단위를 하나로 제한하더라도 완료 여부 확인은 필요하다.

**개선:** 구현 제출과 최종 수락을 분리한다. 최소 상태는 `ready → running → submitted → accepted`, 예외는 `blocked`와 `rework`면 충분하다. worker는 구현 결과와 검증 근거를 제출하고, 검토자가 수락한 뒤 활성 인박스를 정리한다. 부분 결과는 기록하되 미완료 상태를 유지한다. 일반 작업마다 사용자 승인을 추가하자는 의미가 아니라, 기술 검수의 상태를 구분하자는 의미다.

### P1 — 모델 배정과 상향 전환 규칙이 없다

근거: [orca-agents.md](../plugins/fullops-squad/assets/repository/.fullops-squad/orca-agents.md), [setup-fullops:12](../plugins/fullops-squad/skills/setup-fullops/SKILL.md).

현재 배정표에는 CLI와 기동 방식만 있다. 같은 CLI에서 어느 모델을 어떤 추론 설정으로 실행할지, 설계·구현·검수 중 누가 무엇을 책임지는지 정해져 있지 않다. 모델 옵션을 사용할 수 있다는 안내는 배정 정책을 대신하지 못한다.

**개선:** 역할과 모델 등급을 분리한다. 프로젝트별로 `planner`, `implementer`, `reviewer`에 CLI·모델·추론 설정·지원 기동 방식을 연결한다. 구체적인 모델 이름과 단가는 프로젝트에서 설정하고 하네스에 고정하지 않는다. 실제 기동 후 요청한 모델을 사용했는지 확인할 수 있는 근거도 기록한다.

| 책임 | 기본 배정 | 산출물과 경계 |
|---|---|---|
| 요구사항 정리·아키텍처·계약 결정 | 고성능 모델 | 결정 근거, 구현 명세, 수락 기준, 위험 분류 |
| 범위가 확정된 코드 구현 | 비용이 낮은 모델 | 정해진 파일·계약 안의 구현, 테스트, 사실 기반 결과 |
| 기계 검증 | 스크립트·기존 빌드 도구 | 명령, 종료 코드, 검사 대상 SHA, 결과 위치 |
| 설계 준수·위험 검토 | 고성능 모델 | 변경 diff와 실패·위험 중심 검수, 수락 또는 재작업 |
| 문서 서식·목차·메타데이터 | 스크립트 | 템플릿 적용, 링크·필수 필드 검사 |

계약 충돌·요구사항 누락·새 보안 경계·동일 실패 반복 등은 구현 모델이 추측을 계속할 조건이 아니라 planner에게 돌려보낼 조건으로 정한다. 예를 들어 동일 원인의 검증 실패 2회 후 상향 전환을 초기 정책으로 삼고 실측으로 조정할 수 있다. 위험한 설계 변경은 구현 단계라도 고성능 모델을 배정할 수 있어야 한다.

### P1 — 구현 모델용 입력 명세가 충분히 고정돼 있지 않다

근거: [handovers/_TEMPLATE.md](../plugins/fullops-squad/assets/repository/.fullops-squad/handovers/_TEMPLATE.md), [fullops-orca:25–30](../plugins/fullops-squad/skills/fullops-orca/SKILL.md).

목표·범위·검증 칸은 있지만 기준 commit, 설계 문서 버전, 정확한 인터페이스와 예시, 수정 금지 영역, unresolved 항목, 상향 전환 조건이 구조화돼 있지 않다. 현재 가시성 검사는 좋은 안내지만 준비된 명세인지 판정하는 자동 검사는 없다.

**개선:** 기존 지시서를 유지하면서 기계가 읽을 작은 메타데이터를 붙인다. 거대한 작업 관리 시스템 대신 과제별 다음 항목부터 시작한다.

- `task_id`, `attempt`, 상태, 구현 담당과 검토 담당, 모델 배정.
- `base_sha`, 설계 참조와 버전, 선행 과제.
- 반드시 읽을 문서·코드, 수정 가능 파일과 소유권.
- 입력/출력·오류·불변 조건·경계 사례·필수 검증 명령.
- 제출해야 할 코드·테스트·문서, 검토 기준, 상향 전환 조건.

dispatch 전에 스크립트로 누락 필드·미해결 placeholder·존재하지 않는 경로·선행 상태를 검사한다. 의미적으로 구현 가능한 명세인지는 planner가 확인한다. 메타데이터와 Markdown에서 같은 상태를 별도 수작업으로 관리하지 않고, 표시는 정본으로부터 생성한다.

### P1 — 문서 본문 템플릿과 공통 문체가 없다

근거: [산출물 매핑](../plugins/fullops-squad/assets/repository/.fullops-squad/docs/deliverables/README.md), [fullops-deliverables](../plugins/fullops-squad/skills/fullops-deliverables/SKILL.md), `assets/repository` 구성.

D01–D13은 원천 경로·상태 표다. 요구사항·설계·QA·운영 문서의 실제 본문 틀, 필수 절, 용어 규칙, 작성 예시가 플러그인에 없다. 한국어로 작성한다는 규칙만으로 문체가 통일되지는 않는다. 외부 스킬이 문서를 생성할 수 있어도 이 플러그인의 공통 형식을 보장하지는 않는다.

**개선:** 공통 작성 규칙 1개와 필요한 문서 종류의 템플릿을 플러그인 자산으로 제공한다. 해당 템플릿만 읽고 생성하게 하며 서비스 레포에 전체 템플릿 라이브러리를 복제하지 않는다. 상세 제안은 6절에 정리했다.

### P1 — 산출물 검사는 품질 게이트로 쓸 수 없다

근거: [deliverables.py:18–48](../plugins/fullops-squad/scripts/deliverables.py).

재현 결과:

- D02를 `approved`로 바꿔도 원천 디렉터리에 `.gitkeep`만 있으면 통과한다. 조립 문서가 없어도 통과한다.
- 존재하는 파일의 없는 `#절`을 링크해도 통과한다. 앵커는 검사 전에 제거한다.

현재 기능은 제한적인 경로 검사다. 필수 내용·요구사항 추적성·승인 근거·테스트 진실성은 검증하지 않는다. 이를 “검증 통과” 한 줄로 보고하면 구현 모델과 검토자가 품질을 오인할 수 있다.

**개선:** `경로 검사`, `문서 형식 검사`, `의미 검수` 결과를 구분한다. 적용 대상 문서만 검사하되, 작성 완료를 주장하는 문서는 비어 있지 않은 원천과 필수 절·메타데이터·유효한 로컬 절 링크를 확인한다. `approved`는 검토자·근거·검토 대상 revision을 함께 요구한다. 코드·테스트의 의미 검증은 실제 실행 근거와 reviewer의 판단이 담당한다.

### P1 — 웹·모바일·게임에 동일한 역할과 D01–D13을 강제한다

근거: [work.py:10,76](../plugins/fullops-squad/scripts/work.py), [deliverables.py:23](../plugins/fullops-squad/scripts/deliverables.py), [역할 배정](../plugins/fullops-squad/assets/repository/.fullops-squad/orca-agents.md).

역할명은 레포에 맞게 바꾸라는 문서와 달리 CLI는 6개 역할만 허용한다. 산출물 검사도 D01–D13의 정확한 집합을 요구한다. DB 관련 D06–D09는 저장소·DB가 중심인 제품에는 유용하지만 모든 게임·모바일 앱에 같은 비중으로 요구할 근거가 없다. 반대로 모바일 오프라인·권한·배포와 게임 프레임 예산·에셋 파이프라인 등은 명시된 계약이 없다.

**개선:** 공통 개발 절차를 유지하고 setup에서 제품 특성과 필요한 능력을 선택한다. 웹·모바일·게임을 배타적인 세 하네스로 나누지 않는다. 모바일+백엔드나 게임+서버를 함께 선택할 수 있어야 한다. 역할은 프로젝트 선언을 따르고 CLI는 이를 검증한다. 납품 계약상 D01–D13이 필요하면 유지하되 `해당 없음`과 사유를 지원하고 추가 문서도 허용한다.

| 범위 | 필요한 추가 설계·검증 예시 |
|---|---|
| 공통 | 요구사항, 도메인, 인터페이스, 보안, 테스트, 배포·운영 |
| 웹 | 브라우저·접근성, 세션·인증, API, 배포 환경 |
| 모바일 | 기기·OS 범위, 권한, 오프라인·동기화, 앱 생명주기, 서명·배포 |
| 게임 | 핵심 게임 루프, 상태·씬, 입력·카메라, 프레임·메모리 예산, 에셋, 저장·멀티플레이 |

이는 공통 하네스가 추가 도구·검증을 선택할 기준이다. 모든 엔진·언어·배포 도구를 하네스 안에 구현하자는 제안은 아니다.

### P2 — 재작업·업그레이드·템플릿 우선순위가 불완전하다

근거: [work.py:12,37,55](../plugins/fullops-squad/scripts/work.py), [setup.py:49,64](../plugins/fullops-squad/scripts/setup.py).

- 이미 아카이브된 task key를 `new`가 받지만 나중에 `finish`가 중복으로 거절한다. 리뷰 반려 후 같은 과제를 재작업하는 흐름이 막힌다. 과제 ID와 시도 번호를 나누고 수락 전에는 재작업을 허용해야 한다.
- 레포의 `_TEMPLATE.md`를 수정해도 `new`는 플러그인 원본을 읽는다. 서비스별 템플릿을 허용한다면 레포 override → 플러그인 기본값 순서를 명시해야 한다.
- setup 재실행은 기존 문서를 보존하므로 이전 `workflows/` 참조와 오래된 `plugin_version`이 그대로 남는다. 보존 동작은 맞지만 업그레이드 절차는 별도로 필요하다. 관리 규약만 버전별 diff로 갱신하고 개발 기록은 유지한다.
- `fullops.json`을 `[]`로 바꾸면 setup은 거부하지만 work와 deliverables는 존재만 확인해 통과한다. 활성화·schema 검증을 공통으로 사용해야 한다.

### P2 — 토큰·재작업 비용을 관찰할 수 없다

근거: 현재 과제·역할·프로젝트 템플릿과 스크립트에 사용량·모델별 시도 기록이 없다.

과제마다 새 세션을 열고, 역할 컨텍스트·하네스 규약·Orca 가이드를 읽고, 구현 후 인박스 보고·phase 로그·context·PLANS·터미널 보고를 관리한다. 각 기록의 목적은 있지만 같은 설명이 반복될 수 있다. 작은 작업까지 전부 worker로 분리하면 분업 비용이 구현 비용보다 커질 수 있다.

**개선:** 역할별 전체 이력 대신 해당 과제에 필요한 설계·코드·결정만 묶어 전달한다. 의미상 독립된 과제는 세션을 분리하되, 같은 계약의 사소한 수정은 하나의 과제로 묶는다. 기록 전문은 보존하고 자주 읽는 요약·인덱스는 스크립트가 만든다. UI 상태를 반복 읽을 때도 필요한 필드만 얻는 방식을 검토한다.

측정 기준은 `수락된 과제당 총비용`이다. 모델별 입력·출력·캐시 사용량(호스트가 제공할 때), 호출/시도 횟수, reviewer 투입량, 상향 전환, 최초 수락률, 검증 실패, 재개방 결함, 지연 시간을 함께 기록한다. 사용량을 얻지 못하면 `unknown`으로 남긴다. 문자 수를 실제 토큰 수처럼 보고하지 않는다.

### P2 — 외부 스킬 설치가 광범위하고 재현성이 낮다

근거: [dependencies.json](../dependencies.json), [install.py:14–42](../scripts/install.py).

`mattpocock/skills`와 portable ponytail은 `*`로 설치하고, 웹 관련 스킬·MCP·스킬 제작 도구도 모든 선택 호스트에 설치한다. `skills@latest`, `codebase-memory-mcp@latest` 및 고정되지 않은 upstream 때문에 동일 FullOps 버전이라도 외부 동작이 달라질 수 있다.

설치된 모든 스킬 본문이 항상 프롬프트에 들어간다고 단정할 수는 없다. 다만 발견 가능한 스킬과 잠재 충돌 범위가 늘고, 호스트별 실제 컨텍스트 비용을 확인하기 어렵다.

**개선:** 사용자가 원한 자동 종속성 설치는 유지한다. 공통 필수 의존성, 제품 특성별 선택 의존성, 플러그인 개발용 도구를 구분하고 필요한 항목만 자동 설치한다. 검증된 버전·출처를 기록하고 host별 실제 설치 결과를 확인하는 doctor 절차를 둔다. 사용자 범위에 설치된 외부 도구의 자체 동작은 FullOps의 레포 활성화 표식으로 통제되지 않는다는 경계도 유지한다.

## 5. 제안하는 최소 실행 구조

```mermaid
flowchart LR
    U[사용자 요구] --> P[고성능 planner: 요구사항·설계·구현 계약]
    P --> G[스크립트: 명세 준비 검사·입력 묶음]
    G --> W[구현 모델: 제한된 범위의 코드·테스트]
    W --> V[스크립트: 검증 실행·근거 수집]
    V --> R[고성능 reviewer: 계약·위험·변경 검수]
    R -->|수락| A[스크립트: 상태·아카이브·산출물 인덱스]
    R -->|재작업| W
    W -->|명세 충돌·반복 실패| P
```

기존 스킬 4개를 우선 유지하면서 경계를 보강할 수 있다. `fullops-work`가 명세와 상태, `fullops-orca`가 실행 전달, `fullops-deliverables`가 문서 규약, `setup-fullops`가 프로젝트 배정을 담당한다. workflow 디렉터리를 다시 만들 필요는 없다.

추가 스크립트는 작업 준비 검사·검증 근거 수집·상태 전이·문서 생성/검사처럼 판단 기준이 명확한 기능부터 만든다. 고성능 모델을 단순 CLI 전달·로그 복사·목차 작성에 계속 사용하지 않는다. 모델이 작성한 임의의 shell 문자열을 검사 없이 실행하는 자동화로 확장하지 않고, 프로젝트에서 정한 검증 명령과 실행 위치를 사용한다.

## 6. 문서 템플릿 제안

문서 전체에 적용할 작성 규칙과 종류별 본문 틀을 분리한다. 우선 공통 템플릿은 제품 개요, 요구사항, 아키텍처/설계 결정, 구현 명세, QA/검수 보고, 운영/인수인계 정도로 묶고 D01–D13이 이를 참조하게 한다. 제품별 추가 절은 필요한 경우에만 붙인다.

**공통 규칙 예시:**

- 문장은 `~한다`, 사실 정의는 `~이다`로 쓴다. 홍보 표현과 막연한 평가를 피하고 검증 가능한 사실을 적는다.
- 확정 사실, 설계 결정, 가정, 미확정을 구분한다. 미확정에는 필요한 입력·담당·해소 조건을 적는다.
- 동일 개념은 프로젝트 용어집의 이름을 사용한다. 요구사항·인터페이스·검증 항목에는 안정적인 ID를 부여한다.
- 수행하지 않은 테스트는 미실행으로 표시한다. 승인·성능 수치·코드 존재를 추정해 채우지 않는다.
- 명령과 코드는 코드 블록에, 상태·비교·추적성은 고정 열의 표에 기록한다.

**공통 메타데이터 예시:** 문서 ID, 템플릿 ID/버전, 제목, 상태, 개정일, 작성/검토 역할, 상위 요구사항, 근거 revision. 승인된 문서에는 승인 근거를 연결한다.

**요구사항 본문 틀 예시:**

```markdown
# <요구사항 ID> — <제목>

## 목적과 사용자
## 범위와 제외 범위
## 동작과 예외
## 수락 기준
| ID | 전제 | 동작 | 기대 결과 | 검증 방법 |
|---|---|---|---|---|
## 제약과 품질 요구
## 미확정 사항
| 항목 | 필요한 입력 | 담당 | 해소 조건 |
|---|---|---|---|
## 연관 설계와 검증 근거
```

각 템플릿에는 짧은 작성 지침과 완성 예시 하나를 제공한다. 생성 스크립트가 파일명·제목·메타데이터·절을 만들고 모델은 내용에 집중한다. 검사 스크립트는 필수 절·ID·상태·placeholder·링크를 확인한다. 문체 규칙 일부는 자동 검사할 수 있지만 내용의 정확성과 자연스러움까지 형식 검사로 보증하지 않는다.

프로젝트가 문서 템플릿을 재정의할 때는 명시적 override로 관리한다. 모든 템플릿을 매번 읽는 대신 요청 문서의 템플릿과 공통 규칙만 읽는다. DOCX/PDF 출력은 같은 원천을 렌더링하고 별도 원문을 다시 작성하지 않는다.

## 7. 복잡도·중복을 줄일 부분

- `shrink:` `deliverables.py`의 `issues`와 `errors`는 현재 모든 추가 경로에서 동일하다. 하나로 합칠 수 있다.
- `shrink:` work와 deliverables의 Git 루트·활성화 확인을 공통 함수로 모으고 setup과 동일한 schema 검증을 적용한다. 현재는 같은 목적의 확인이 서로 다르다.
- `shrink:` 역할별 고정 슬롯은 프로젝트 배정으로 대체하고 실제 사용하는 역할의 파일·워크트리만 만든다. 작은 작업마다 6역할을 거칠 필요는 없다.
- `shrink:` phase 상세 로그·완료 보고·터미널 보고에 같은 내용을 재작성하는 대신 결과 정본에서 요약을 생성한다. 장기 로그 보존과 반복 프롬프트 입력량을 분리한다.
- `yagni:` 모든 프로젝트에 설치되는 제작 도구·웹 도구는 해당 기능을 선택한 프로젝트에만 자동 설치한다. 플러그인·스킬을 개발하지 않는 worker에게 제작 도구를 기본 요구할 이유는 약하다.

단순 삭제만으로 가능한 중복 제거는 `issues`/`errors` 4줄 정도다. 더 큰 절감은 줄 수보다 설치 범위·반복 읽기·재작업 감소에서 나온다. 외부 의존성 몇 개를 공통 설치에서 제외할지는 프로젝트 기능 선택에 따라 달라지므로 고정된 절감 수치를 제시하지 않는다.

## 8. 권장 구현 순서와 성공 조건

| 순서 | 작업 | 성공 조건 |
|---|---|---|
| 1 | 완료·검수 상태 분리, 재작업 attempt, schema 검사 | blocked/미검증 작업은 활성 목록에서 사라지지 않고 리뷰 반려 후 재제출 가능 |
| 2 | 모델 배정과 구현 명세 계약 | 실제 모델 배정이 확인되고, 필수 입력 누락·기준 SHA 불일치가 dispatch 전에 발견됨 |
| 3 | 공통 문서 템플릿·작성 규칙·제품 특성별 적용 | 웹·모바일·게임 표본 문서가 동일한 메타데이터·문체를 쓰고 불필요한 문서는 사유와 함께 제외됨 |
| 4 | validator 강화와 템플릿 override·업그레이드 | 빈 approved 문서·없는 절 링크가 검출되고 프로젝트 수정·기록을 보존하며 규약만 갱신됨 |
| 5 | 비용·재작업 계측, 의존성 선택, 입력 묶음 생성 | 같은 수락 기준의 과제에서 전체 고성능 모델 방식과 혼합 모델 방식의 총비용·품질·시간 비교 가능 |

검증 과제는 최소 웹 기능 하나, 모바일 기능 하나, 게임 기능 하나로 선정한다. 각 과제에 정상 동작·실패·경계 조건과 문서 예시를 먼저 고정한다. 한 번의 성공으로 전체 제품군 지원이나 절감률을 일반화하지 않는다. 현재 역할별 파일·스킬·setup의 기반을 살리면서 위 순서로 보완하는 편이 전면 재작성보다 작고 검증하기 쉽다.
